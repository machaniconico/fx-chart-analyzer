# 歴史データの完全性と独立した巻戻し検知

対象は仮想研究の準備のみ。既存EA・共有台帳・保存済みチェックポイントを変更せず、観測データでの再評価・定期実行・採用・実注文は行わない。

## 読取専用のチェックポイント監査

```bash
node scripts/audit-research-history.mjs \
  --checkpoint=PRIVATE_QUIESCENT_COPY \
  --ledger-id=EXISTING_LEDGER_ID \
  --manifest-sha256=INDEPENDENTLY_RETAINED_MANIFEST_SHA256
```

`--manifest-sha256` は任意。別に信頼して保持した値がない場合は省略し、同じディレクトリから計算した値を独立した証拠と呼ばない。出力には非公開の記録IDと台帳案が含まれるため、公開リポジトリ・CIログに置かない。

処理は次を確認する。

- manifestに列挙されたファイルと実際の全ファイルの集合が一致すること。未列挙ファイル、欠損、危険なパス、symlink、hardlink、過大な入力を拒否する。
- 各ファイルのSHA-256と、存在する場合のmanifestの外部pin。
- すべての `audit.jsonl` のハッシュ鎖、イベントと成果物の参照・ハッシュ、使用済み予約。同じ履歴のコピーは既存の移行処理で照合する。共有台帳の状態をローカルの記録から再構築しない。
- 旧tunerの `.selected.json` があれば、そこに記載された元レポートのSHA-256に一致する完全版がこのコピー内にあるか。存在確認だけで完全版の意味・全試行を検証済みとはしない。

元ファイルは読むだけであり、台帳案を保存・適用しない。正常な監査でも終了コードは **3**、`activationReady` と `historicalCompletenessProven` は常に **false**。不一致・破損時は終了コード **2**。`knownReservationEnd` は確認できた予約の下限情報であり、その直後が未使用データである証明ではない。

ファイルの読取前後と全体の最終確認で通常の同時変更を検出するが、稼働中のディレクトリを原子的にsnapshotsするものではない。停止済みのコピーに使う。管理者やOSによる能動的な改変への保証、署名の検証、独立保管者の証明はない。

## 「ファイルが一致」と「全履歴がそろう」は別

manifestと監査鎖が正常でも、正常なprefixだけを残して新しいmanifestを作れば自己整合性は保てる。別の信頼できる保存先に以前のmanifest hashを保持していれば、その既知checkpointからの削除・変更は検出できる。しかし、そのcheckpoint以前から欠けていた実験や、別のPC・枝・旧tunerで行った実験は証明できない。

旧tunerの選抜済みレポートは全試行記録ではない。候補数・試行総数や期間の長さだけで、各検証区間の正確な開始・終了を復元しない。過去の新しいautonomy journalが一件だからといって、過去の検証区間が全体で一件とは扱わない。

有効化前に必要なもの:

1. 対象を明示した全実験元の一覧。旧tuner、手動探索、別PC、以前の保存版、失敗・中断実行も含む。
2. 各元の正確な消費済み区間と最終ハッシュ、または根拠を持つ保守的な使用済みcutoff。
3. 得られない元や時刻の範囲が不明なら停止。短い推測のcutoffで埋めない。将来から検証を始める場合も、まず旧経路の評価を止め、cutoverを記録し、その時点より後に収集したデータだけを未使用候補にする。これは**提案**であり、このツールはcutoffも旧経路も変更しない。
4. 既存の共有予約を一つも失わず照合する。元の正確な予約を保ったままcutoffを追加できるが、別途承認・検証した移行が必要。空台帳への置換では解決しない。

## 独立した巻戻し検知の選択肢

Gitのimmutable commitと非force更新は並行書込に有用だが、同じ管理権限でbranchとcheckpointを両方戻せるなら、独立した巻戻し防止ではない。別branch、同じrepositoryのtag、ローカルlockfile、通常のActions artifactやcacheだけでは足りない。branch保護の変更もこの作業では行わない。

候補は次の二つ。いずれも未構築であり、設定・権限・保持期間を実サービスで確認する必要がある。

- **別管理境界の追記専用witness**: 記録の削除・過去版復元を通常の研究writerができない保存先。単調な連番、対象ledger ID・repository・branch・path、予約の識別子と区間、過去記録のhashを保持する。WORM/retention設定だけでなく、変更できる管理者・保存期間・独立した認証境界・障害時の復元も確認する。別providerでも同じwriterが両方を自由に巻き戻せるなら十分でない。
- **所有者が別に保持する固定pin**: 特定checkpointへの巻戻し検知には使えるが、各サイクルの更新を独立して保管するまで次へ進めない。半自動運用の出発点にはなるが、単独で常時自律運転にはならない。Spaceの既存version付きバックアップは復元の別コピーにはなるが、通常のreplace/restore権限と実際の保持保証を確認しない限りWORM witnessではない。

新しい秘密鍵・API token・権限の追加はここでは行わない。コードの受入試験と、providerの災害耐久性・管理者攻撃の保証は分けて記録する。

## high-waterを後から保存するだけでは残る隙間

`台帳CAS → 外部pin保存` だけだと、台帳CASの直後にprocessが落ち、pin更新前に台帳を戻された場合、新processがその使用済み予約を知らない可能性がある。現在のGit transportの `minimumCommit` も、この空白を自動で埋めるものではない。

将来の独立witnessは**write-ahead方式**にする。

1. 独立した権威あるwitnessを読み、最後の連番・hash・未解決intentを確認する。消失・不一致・古い応答なら停止し、空のwitnessを自動作成しない。
2. fitting前に、計画全体の全holdout区間・要求hash・engine hash・一意なattemptをwitnessへ条件付きで追記し、正確なreceiptを再読取する。この時点から全区間を使用済みと扱う。
3. そのintentを共有台帳へ予約し、正確なreceiptを確認する。その後witnessに台帳commit・本文hashを紐づけて追記する。二つの保存先は単一transactionではないので、部分成功は保守的に停止・消費済みのまま残す。
4. 両方が整合した時だけfittingを始める。結果も両方へ順に保持・照合する。応答喪失は正確なreceiptのreadbackでのみ解決し、未確認のwriteを再送しない。
5. 再起動で未解決intentがあれば再利用・自動引継ぎをせず停止する。台帳側の消失・rollbackを検出したら、別途承認した復旧で元の全消費を保存するまで進めない。

この文書はprotocol案であり、witnessの実装・接続・本番有効化ではない。既存のsynthetic-only制約を解除しない。次の実装には、独立writerの競合、各await前後のSIGKILL、片側のみ書込成功、両方向rollback、古い応答、未解決intentと保持期限の試験が必要。
